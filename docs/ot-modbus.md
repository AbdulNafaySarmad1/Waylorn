# Modbus TCP read-only pilot

`crates/ot-core/src/modbus_tcp.rs` implements bounded function 03 (holding-register) and function 04 (input-register) reads. It has no write API. The existing Rust operation gate must allow `Read` for an explicitly declared device before a TCP socket opens. New or unknown devices remain denied. A caller supplies a specific socket address and unit ID; this module does not scan networks or discover devices.

The reader limits quantity to 1–125 registers, rejects address wraparound, uses a caller-provided timeout capped at 10 seconds, and opens one connection per request. It checks the transaction ID, protocol ID, unit ID, MBAP length, function code, and byte count before accepting values. Response allocation is bounded to 252 bytes. Device exception responses are returned without an automatic retry. The loopback simulator tests cover a valid read, gate denial, a mismatched transaction ID, an exception response, and an oversized response.

The bounds and frame checks follow the [Modbus Application Protocol Specification V1.1b3](https://www.modbus.org/docs/Modbus_Application_Protocol_V1_1b3.pdf) and [Modbus Messaging on TCP/IP Implementation Guide V1.0b](https://www.modbus.org/docs/Modbus_Messaging_Implementation_Guide_V1_0b.pdf). This is a software pilot, not a device compatibility claim. A loopback simulator now sends values through Rust, Go, Keycloak, .NET, and site-local PostgreSQL. The reader also performs Read Device Identification (0x2B/0x0E, basic objects) on the configured endpoint only; the result is a discovery claim for human reconciliation (ADR 0036). Before connecting to real equipment, define an approved address/port allowlist, per-device polling budget, register map and scaling, network isolation, credential and identity handling where supported, operator consent, and a site-specific test plan. The local process JSON contract is not the planned authenticated Protobuf RPC boundary.
